# Stale-sync recovery и идемпотентность TEMP-замеров

Дата реализации: 2026-07-26.

## Область изменения

Изменение относится только к синхронизации локальных TEMP-замеров и их offline-фото.
Supabase schema, RLS, Auth, production data, upload UX и SVG runtime не меняются.
`sync_queue` существует в IndexedDB как зарезервированный store, но текущий runtime не записывает
в него операции: активными durable-операциями являются строки `offline_drafts` и
`offline_photos`.

Центральный контракт находится в `sync-state.js`. `app.js` использует его для startup recovery,
переходов состояния, reconciliation и сериализации операций.

## Контракт состояний

| Статус | Значение | Можно повторить |
| --- | --- | --- |
| `local_only` | локальная операция ещё не отправлялась | да |
| `pending` | исторический/очередной ожидающий формат | да |
| `syncing` | активная попытка с `sync_attempt_started_at` | только после timeout |
| `sync_error` | попытка завершилась ошибкой или была восстановлена как stale | да |
| `error` | исторический формат ошибки | да |
| `retry` | исторический явно повторяемый формат | да |
| `synced` | есть подтверждённое серверное завершение | нет, кроме оставшихся фото |

Каждая попытка сохраняет:

- `sync_operation_id` (`local_id` замера или `local_photo_id`);
- `sync_attempt_started_at`;
- `sync_attempt_count`;
- `last_sync_error`;
- серверные идентификаторы, полученные до сбоя.

`last_sync_error` и счётчик попыток не стираются при начале retry. Текущая ошибка очищается только
при начале/успешном завершении попытки.

## Stale timeout

Явный timeout — **5 минут**.

- `syncing` моложе 5 минут остаётся активным и не сбрасывается.
- `syncing` старше 5 минут переводится в `sync_error`.
- исторический `syncing` без `sync_attempt_started_at` считается прерванным после restart.
- если локальная запись уже содержит полное серверное подтверждение, она становится `synced`, а
  не retryable.
- для фото подтверждение принимается только при совпадении server measurement id с TEMP→real
  mapping замера.

Startup recovery не создаёт и не изменяет серверные записи. Перед последующим create приложение
всегда сверяет Supabase.

## Reconciliation перед create

### Замер

До первого запроса создаётся один `planned_server_number` и сохраняется в IndexedDB. Все retry
используют тот же номер. Перед insert выполняется точный запрос по:

- `number`;
- `created_by` текущего пользователя.

Найденная строка дополнительно должна согласоваться с сохранённым `server_client_id` либо с
точными client metadata и с заполненными основными metadata TEMP-замера. Совпадение номера без
этого подтверждения считается конфликтом и не разрешает create.

Одна запись восстанавливает TEMP→real mapping. Ноль записей разрешает create. Несколько записей
считаются неоднозначным состоянием: create останавливается.

### Клиент

Если `server_client_id` уже сохранён, используется он. Иначе перед insert выполняется точная
сверка доступных существующих полей:

- `created_by`;
- `name`;
- `phone`;
- `address`;
- `city`.

Один точный кандидат переиспользуется. Несколько кандидатов останавливают автоматический create.

### Фото

Путь offline-фото остаётся детерминированным:

`measurements/<real-measurement-id>/<local-photo-id>.<ext>`

Перед upload приложение делает точный `Storage.list()` в целевой папке. Существующий объект с
точным именем не загружается повторно. Перед insert строки приложение ищет точное сочетание
`measurement_id + file_path`; существующая строка переиспользуется. Повторные строки не
создаются и существующие дубликаты не удаляются автоматически.

Серверная связь фото с другим measurement id никогда не перепривязывается. Она переводится в
ошибку для ручной диагностики.

## Сериализация

Конфликтующие операции одного `local_id` выполняются последовательно. В одной странице
повторный вызов получает тот же Promise. Между вкладками используется Web Locks API, если он
доступен. Разные measurement id не блокируют друг друга.

## Проверки

Детерминированный suite `tests/sync-state.test.js` покрывает:

- stale `syncing` после restart;
- потерянный ответ после серверного завершения;
- истинную ошибку и безопасный retry;
- повторный и конкурентный retry;
- предотвращение duplicate client/measurement/photo row/Storage path;
- переиспользование TEMP→real mapping;
- сохранение non-stale операции;
- независимую синхронизацию разных замеров;
- остановку при неоднозначной сверке.

Регрессии путей и reopen фото остаются в `tests/photo-path.test.js`.

## Безопасность выпуска

- реальный Storage не просматривается и не изменяется во время автоматических тестов;
- schema/RLS/Auth/environment не меняются;
- deploy не выполняется;
- `drawing-bridge.js` и `svg-constructor/embedded.html` не меняются;
- перед merge требуется отдельная acceptance на изолированном staging после owner approval.
